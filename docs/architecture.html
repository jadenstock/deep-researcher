Deep Research Agent — Architecture

A precise specification of the agent architecture, sourced from src/deep_research_agent/. Click any panel to expand.

Pipeline at a glance

Landscape — wide-filter recon Researcher — plans & reviews Analyst — investigates a sub-question Scout — search, triage, skim Shared memory (notes)

Entry point research_run(deps, query) in researcher.py:383 runs the whole pipeline. Landscape blocks first; the researcher then dispatches up to 8 analyst calls; each analyst may dispatch up to 4 scout calls in parallel. All coordination happens through the NoteMemory graph — there is no RunState, no agent_outputs dict, no message passing between agents outside of tool args.

What each level sees

The hierarchy is also an information filter. Each layer upward hides the raw source text that the layer below wrestled with — so the researcher can plan without drowning in document content, and the analyst can investigate without running its own searches.

What flows up (amber) is synthesized; what flows down (grey) is scoped instruction.

The four agents

Each agent is a PydanticAI tool-using loop driven by drive_agent() (agents/_run.py:30-86), which instruments agent lifecycle events, scopes a _CURRENT_AGENT_ID contextvar, and records token usage.

Strategy & prompt shape

Single agent.iter() loop. The system prompt tells the model to run parallel searches with varied query formulations, create source notes for every candidate (dedup is automatic via URL normalization), consult list_source_notes to spot coverage gaps, and only then call write_landscape_brief with a short markdown report covering themes, positions, key sources, under-covered areas, and tier distribution.

The brief is stored on the LANDSCAPE note's content field, and its structured fields (themes, positions, under_covered_areas, tier_distribution, peer_review_fraction) live in LandscapeMetadata.

Strategy & prompt shape

RESEARCHER_SYSTEM (researcher.py:57-227) enforces four disciplines:

  1. Classify before dispatching. Each sub-question is tagged lookup / synthesis / contested / sparse — this is persisted on the QUESTION note via QuestionClassification.
  2. Mode selection. explore for fresh investigation, verify for an independent re-check of load-bearing claims, adversarial for a counter-case. Verify/adversarial run on a different model family than explore.
  3. Budget discipline. Only verify/adversarial-dispatch claims that are load-bearing; don't burn the budget cross-checking everything.
  4. 5-check pre-commit audit before calling answer_question: sufficiency, source grounding, thin-spot scan, contradiction, direction.
Tool semantics
  • get_research_state() — snapshot of every question (status + confidence), sources grouped by tier and state, remaining analyst budget.
  • investigate_question(question, mode) — creates a child QUESTION note, dispatches an analyst under drive_agent, decrements the budget.
  • load_note(note_id) — re-reads a QUESTION note's synthesis. Researcher deliberately never loads SOURCE notes; it only sees what analysts synthesized.
  • answer_question(...) — terminal; writes report_markdown, confidence, sources_cited, disagreements, open_issues into the root question and returns.

Mode routing

The mode parameter conditionally routes the model (analyst.py:221-231):

ModeRole classTierPrompt emphasis
explore GENERATIVE MID Fresh investigation of the sub-question.
verify JUDGMENT MID Load a prior claim note; phrase queries to find counter-evidence; explicitly state SUPPORTS / REFUTES / INCONCLUSIVE.
adversarial JUDGMENT MID Load a prior position note; steelman the opposite; lead with the counter-case.

Verify/adversarial come from a different model family than explore, enforced by the routing config (config/routing_diverse.yaml).

Reading protocol & prompt emphasis

ANALYST_SYSTEM (analyst.py:100-218) is explicit about the scout/read separation:

  • Call list_source_notes() first — reuse what's already in the graph before launching scouts.
  • Dispatch scouts only for uncovered angles (up to 4 parallel).
  • For each candidate, load_note(source_id) to read the full cleaned markdown (populated by scout_fetch onto note.content).
  • After reading, update_source_after_reading(...) appends a ReadingEntry tagged with this analyst and this question — so the same source can be read differently by different analysts for different questions without overwriting.
  • Claims must be verbatim-quoted; relevance_note explains why the claim matters for this angle.
  • Tier-4 (community blog) sources are background only — never anchor a core claim to one.
  • Limitations and competing approaches are stated explicitly; they are not optional.

Columnar search-skim-commit flow. Optional citation walk branches off round 2; thin rounds loop back with re-phrased queries.
Strategy — the 3-round search-skim loop
  1. Check the corpus first. list_source_notes() shows what the graph already has. Prefer existing hits to re-searching.
  2. Round 1 — broad searches. 2–4 parallel search_web / search_academic calls with varied query formulations. Every candidate gets create_source_note (automatic URL dedup).
  3. Round 2 — skim. scout_fetch the top 6–8 candidates. This does a light fetch (HTML via trafilatura or PDF via MarkItDown), writes cleaned markdown onto note.content, and returns a 2–3 sentence preview.
  4. Optional — citation traversal. For high-signal sources with a DOI or arXiv id, find_related_papers can walk the citation graph (citing / cited_by) via Semantic Scholar.
  5. Optional — reformulate. If the first pass came up thin, one more round of searches with different phrasings.
  6. Commit. commit_scout_result appends to a closure-scoped outbox list on the caller; the scout returns.
Tier guesses & relevance

Scouts attach two rough signals per source:

  • tier_guess ∈ 1..5 — 1 peer-reviewed · 2 arXiv · 3 industry · 4 community · 5 low-quality.
  • relevance_guess — is this source about the specific angle, not just the broad topic?

Both are guesses; the analyst is free to overrule them when they read the source and append a ReadingEntry with the final tier.

Shared state — the note graph

NoteMemory (agents/memory.py:45-140) is the only mutable state shared across agents. It is an async-safe dict protected by asyncio.Lock, with two secondary indexes for fast lookup by note type and by source URL. All create() / update() operations serialize under the lock; get() takes stale snapshots without locking.

Note types

LANDSCAPE

One per run. Created eagerly in research_run, updated by the landscape agent. content holds the markdown brief; LandscapeMetadata holds structured fields (themes, positions, key_sources, under_covered_areas, tier_distribution, peer_review_fraction).

SOURCE

SCOUTED → FETCHED → ANALYZED
  • SCOUTED — created from a search result, title + snippet only.
  • FETCHED — after scout_fetch: cleaned markdown on content, tier classified.
  • ANALYZED — one or more analysts have appended a ReadingEntry.

Secondary index _by_source_url keeps create operations idempotent under URL normalization. Each source carries an append-only readings: list[ReadingEntry], so N analysts can read the same source for different questions without losing any perspective.

QUESTION

IN_PROGRESS → SYNTHESIZED

Root question created by research_run for the user's query; sub-questions created by the researcher via investigate_question. QuestionMetadata carries classification, status, parent_question_id, report_markdown, confidence, sources_cited, disagreements, open_issues, and answered_by_agent_id.

Concurrency model
  • Single asyncio event loop for the whole run.
  • PydanticAI dispatches parallel tool calls naturally (asyncio.gather-style).
  • NoteMemory mutations serialize under asyncio.Lock.
  • Event publisher calls happen after the lock is released.
  • _CURRENT_AGENT_ID is an asyncio-aware contextvar set by drive_agent, so nested tool invocations are automatically tagged with the right agent.

Tools

Three tool families, declared once and attached to the relevant agents. Every tool is wrapped with @instrumented (agents/events.py:172-225), which emits on_tool_start / on_tool_end events tagged with the current agent id.

Search tools — agents/tools/search.py
  • search_web(query, count=8) — Brave web search.
  • search_academic(query, limit=6) — Semantic Scholar + arXiv.
  • find_related_papers(source_id, direction, limit) — citation traversal via Semantic Scholar.

All return a uniform SearchResult shape (title, url, snippet, source, authors, venue, year, citation_count, pdf_url, doi).

Fetch tools — agents/tools/fetch.py
  • fetch_url(url) — HTML via trafilatura, PDF via MarkItDown. Returns a FetchedContent capped at 60KB.
  • scout_fetch(source_id) — skim variant: fetches url or pdf_url, writes cleaned markdown onto the source note's content, returns a short preview.
Note tools — agents/tools/notes.py
  • create_source_note(...) — create or return existing SCOUTED note (URL-deduplicated).
  • load_note(note_id) — read any note by id.
  • list_source_notes() — compact inventory (state, has_content, n_readings, analyzed_for_questions, tier, topics, summary).
  • update_source_after_reading(...) — append a ReadingEntry (by_agent_id, for_question_id, claims, relevance_note).
  • answer_question(...) — terminal for analyst/researcher.
  • write_landscape_brief(...) — terminal for landscape.
  • commit_scout_result(...) — terminal for scout, via outbox closure.

Retrieval layer

Clients & rate limiting — retrieval/
  • BraveClient — web search; rate-limited (default 1 req/s).
  • SemanticScholarClient — academic search, get_paper, get_citations, get_references.
  • ArxivClient — preprint search.
  • fetch_and_extract() — HTML via trafilatura, PDF via MarkItDown (cap 15MB / 20 pages / 45s).

Rate limits are process-wide token buckets configured once at CLI startup (cli.py:125 → apply_retrieval_rate_limits). A single pooled httpx.AsyncClient is shared across all retrieval.

Events & observability

EventPublisher (agents/events.py:51-108) is a protocol with six hooks. The CLI run path uses a no-op publisher; the server path uses SessionPublisher, which writes events into a RunSession for WebSocket replay.

Hook list
  • on_agent_start(agent_id, agent_type, goal, tier, role, model_id, mode)
  • on_agent_done(agent_id, agent_type, status, verdict)
  • on_note_created(note)
  • on_note_replaced(note)
  • on_tool_start(agent_id, tool_call_id, tool, summary)
  • on_tool_end(agent_id, tool_call_id, tool, status, summary, duration_ms)
  • on_token_usage(agent_id, agent_type, model_id, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens)

Design principles

  1. Memory is the graph. No RunState, no agent_outputs. Agents communicate through shared NoteMemory.
  2. Tool commits are terminal. Each agent type has exactly one commit tool (answer_question, write_landscape_brief, commit_scout_result).
  3. URL dedup at creation. Scouts and landscape can race; find_source_by_url guarantees idempotency.
  4. Tier-conditional routing. Verify/adversarial always come from a different model family than explore.
  5. Multi-reader sources. ReadingEntry stack lets N analysts read the same source for different questions without overwriting.
  6. Progressive disclosure up the tree. Researcher never sees raw source text — only scout previews + analyst syntheses. Analyst never calls search directly — scout does.
  7. Async concurrency with locked mutations. PydanticAI fans out parallel tool calls; NoteMemory serializes writes under a lock; contextvars propagate agent_id.
