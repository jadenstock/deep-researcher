Motivation

Why this project is a multi-agent system rather than a single agent in a loop.

The short version: a single agent with web access and a tool loop is the cleanest possible design for deep research — and the reason we don't build it that way is that it fails on speed, context, and bias. Multi-agent systems aren't a fashion choice; they're the smallest structure that addresses all three at once.

The ideal world

One agent, one loop, one answer.

In an ideal world, deep research is trivially simple to describe:

  • A single agent accepts a question.
  • It has one tool: the web.
  • It runs a loop — fetch, read, reason, decide what's missing, fetch again — until it believes it has an answer.
  • It writes the answer.

Everything about this is appealing. There's no orchestration, no hand-offs, no shared memory to reconcile, no prompt-engineered personas, no budget bookkeeping. The model does what it does best: reason, decide, act, repeat. If you could get this to work, you should. Any more structure than this is overhead that needs justification.

The reason this project looks the way it does is that the simple loop breaks on three specific axes, and each one forces a piece of structure.

Why the simple loop breaks

Three failure modes, all unavoidable at research depth.

1. Speed

A single agent is inherently serial. It fetches one source, reads it, decides what to fetch next. For a question that requires fifty sources, that's fifty sequential round-trips to the model and the web. Research time scales linearly with corpus size, with no headroom to trade compute for latency.

2. Context rot

Every fetched page, every reasoning step, every intermediate conclusion lives in the same context window. At depth, the token count blows past any model's limit — and well before that, quality degrades. Early evidence gets buried, attention diffuses, and the agent starts contradicting its own earlier reasoning.

3. Bias lock-in

A single agent following its own reasoning thread gets tracked into a direction early and cannot get itself out. Once it has framed the question a certain way, every subsequent fetch confirms that framing. Prompting alone — "consider alternative angles," "steelman the opposite" — doesn't reliably break the track, because the same context that produced the bias is still driving the next decision.

Each problem on its own is fixable with a hack. All three at once is a structural problem, and the structure that solves it is multi-agent.

Why a multi-agent system is the answer

One-to-one mapping from the three failures to three pieces of structure.

A multi-agent system isn't a grab-bag of personas. It's a minimal answer to the three failure modes above: one structural feature per problem.

Speed
Problem: serial fetch-reason-fetch loop.
Structural fix: parallelism. Sub-agents run concurrently — many sub-questions investigated at once, many sources fetched at once — so wall-clock time stops being tied to corpus size.
Context
Problem: a single context absorbs every raw source and every intermediate thought.
Structural fix: hierarchy of responsibilities. Each agent holds only what its role requires — the orchestrator sees summaries, not raw pages; the fetchers see pages, not the full question graph. Context stays bounded at every layer.
Bias
Problem: one reasoning thread gets stuck in its own framing.
Structural fix: methodology baked into distinct roles. Different agents are explicitly tasked with explore, verify, and adversarial reads, with different prompts and different models. The system challenges its own conclusions by construction, not by asking politely.

None of these three fixes is available in a single-agent loop. You cannot parallelize a serial reasoning thread. You cannot bound the context of a single agent that has to see everything. You cannot reliably un-stick an agent using the same context that got it stuck. Multi-agent is the minimum viable shape.

The professor and the grad students

The intuition the design is built around.

Imagine a professor and a group of grad students learning a new area together.

The professor does not try to read every paper themselves. They hand each student a sub-question — "go figure out what's known about X," "go find the best three sources on Y," "go argue the opposite of what we think we're converging on." The students disappear for a while. They come back and present what they found. The professor listens, synthesizes, and decides where the gaps still are. They send the students out again on sharper missions. This continues until the professor has a clear lay of the land.

This is what the system implements, more or less literally:

Professor
maps to the researcher — holds the question, dispatches sub-questions, decides when to stop.
Grad students
map to the analysts — each owns a sub-question, each comes back with a synthesized answer.
Library runners
map to the scouts — they fetch and skim sources so analysts don't burn their own context on raw pages.
First lit-review pass
maps to the landscape agent — before anyone goes deep, someone walks the territory once and leaves a map behind.

The analogy is not just aesthetic. Each role solves one of the three failure modes: the students give you parallelism, the hand-off between professor and students keeps each person's context bounded, and the fact that different students can be given different framings (including adversarial ones) is what keeps the group from getting collectively stuck.

What the rest of the design follows from

The specifics, in one sentence each.
  • Agent-driven orchestration. The professor decides when to stop, not a harness timer — because "is the lay of the land clear?" is a judgment call that lives inside the loop, not outside it.
  • Shared append-only note graph. The students' findings need to survive past their own contexts and be re-readable by the professor and by each other — that's the blackboard the group writes to.
  • Progressive disclosure. The professor reads summaries, not raw papers; the students read papers, not the full question tree. Each layer sees exactly what its role requires, and no more.
  • Three analyst modes — explore, verify, adversarial. Methodology-as-structure: the anti-bias argument isn't that the model tries harder, it's that different agents with different framings do fundamentally different work.
  • Role-to-model routing. Generative roles get a generative model; judgment roles get a different model family. Diversity at the judgment layer is the cheapest form of independent review available.
  • Budgets, not replans. A professor with an unbounded reading list is the same failure mode as a single agent with an unbounded context — bounded work per role is what keeps the system from sliding back into the problem it was designed to avoid.

Every one of these is a consequence of the same argument: the simple loop is the thing you'd want, the three failure modes are the reason you can't have it, and the multi-agent structure is the smallest answer that addresses all three at once.
